# 화이트체커 (WhiteChecker)

발행 전 원고의 '사실 취약점'을 먼저 찾아 주는 팩트체크 에이전트입니다. 라이너 .EXE-THON 2026 출품작입니다.

원고를 넣으면 사실 확인이 필요한 문장을 뽑아 공개 자료와 대조하고, 문장마다 판정과 근거, 수정안을 보여 줍니다. 수정안을 받아들일지는 편집자가 정합니다. 고른 것만 반영한 수정 원고와 검토 기록을 내려받습니다.

- 배포본: <https://whitechecker-czawcxfcdhg6ewcy.koreacentral-01.azurewebsites.net>
- 데모 영상: [제출 전에 채움]
- 요구 사항과 설계: [화이트체커_PRD.md](화이트체커_PRD.md)

배포본은 접속 코드가 있어야 쓸 수 있습니다. [접속 코드를 받는 곳: 정해지면 채움] 소스를 직접 실행할 때는 접속 코드가 필요 없습니다.

## 어떤 문제를 푸는가

- 뉴스레터는 한번 보내면 고칠 수 없습니다. 그래서 발송 전에 원고의 사실을 출처와 다시 대조합니다.
- 초안과 1차 확인에 AI를 써도, AI가 '확인됨'이라고 한 내용이 틀릴 때가 있습니다. 마지막 확인은 편집자에게 남습니다.
- 화이트체커는 이 재확인을 맡습니다. 원고가 맞다고 전제하지 않고, 근거가 채워질 때만 '일치'로 판정합니다.

## 처리 흐름

1. **명제 추출**: 원고에서 사실 확인이 필요한 문장을 뽑아 명제로 나누고, 유형과 한정 표현('가장', '최초', '매일' 등), 기준 시점을 적습니다.
2. **근거 모으기**: 명제마다 웹을 검색하고, 검색 결과의 페이지를 직접 열어 본문에서 발췌를 잘라 냅니다. 통설, 최상급, 인용에는 반대되는 근거도 일부러 찾습니다.
3. **판정**: 발췌와 명제를 대조해 일치, 불일치, 근거 부족, 해석 주의로 나눕니다. 공개 자료로 확인할 수 없는 문장은 '직접 확인'으로 따로 모읍니다.
4. **수정안**: 근거가 뒷받침하는 만큼만 문장을 고친 수정안을 만듭니다. 대신 쓸 사실을 확인하지 못하면 수정안을 내지 않습니다.
5. **편집자 검토**: 판정표는 틀린 것으로 확인된 문장부터 보여 줍니다. 문장마다 수정안을 채택하거나, 고쳐 쓰거나, 보류합니다. 고쳐 쓴 문장은 그 문장만 다시 검증할 수 있습니다.

## Liner API를 사용한 기능

모든 호출은 서버에서 하며, 키는 환경 변수 `LINER_API_KEY`에서만 읽습니다([lib/liner.ts](lib/liner.ts)).

| 단계 | Liner API | 하는 일 | 코드 |
| --- | --- | --- | --- |
| 명제 추출 | Model API, `routing_strategy: quality` | 원고에서 명제, 유형, 한정 표현, 기준 시점, 검색어를 뽑음 | [app/api/extract/route.ts](app/api/extract/route.ts), [lib/prompts/extract.ts](lib/prompts/extract.ts) |
| 근거 모으기 | Search API(웹) | 명제마다 기본 검색어 2개. 통설, 최상급, 인용에는 반증 검색어 1개를 더함. 운영 정보와 수치·통계는 검색어 하나를 `date_range: past_year`로 좁혀 최근 내용을 찾음 | [lib/gather/run.ts](lib/gather/run.ts) |
| 추가 검색 판단 | Model API, `routing_strategy: cost` | 모은 자료를 보고 한 번 더 검색할지와, 겨냥할 기관 사이트(`site:`)를 정함 | [lib/prompts/more-search.ts](lib/prompts/more-search.ts) |
| 판정 | Model API, `routing_strategy: quality` | 발췌와 명제를 대조해 판정, 한정 표현별 결과, 고칠 내용을 냄 | [lib/judge/run.ts](lib/judge/run.ts), [lib/prompts/judge.ts](lib/prompts/judge.ts) |
| 보강 검색 | Search API(웹), Model API(`cost`) | 판정이 '근거 부족'이거나 반박 근거가 한 곳뿐이면, 모자란 근거를 겨냥해 한 번 더 찾음 | [lib/run/followup.ts](lib/run/followup.ts) |
| 수정안 | Model API, `routing_strategy: quality` | 한 문장의 고칠 내용을 수정안 하나로 합치고 이음매를 다듬음 | [lib/merge/run.ts](lib/merge/run.ts), [lib/merge/polish.ts](lib/merge/polish.ts) |

- Search API는 `POST /tools/search/web`을 씁니다. Premium Data(`include_knowledge`)는 끕니다.
- Model API는 `POST /chat/completions`에 `liner-claude-router-1.0` 모델과 `routing_strategy`를 지정합니다. 출력은 `response_format`의 JSON 스키마로 받고, `prompt_cache_key`로 지시문을 캐시합니다.
- 다시 시도는 Liner의 응답(`retryable`, `retry-after`)을 따릅니다.
- 화면 위쪽 줄에 검색과 모델 호출 횟수, 어림한 비용, 걸린 시간이 나옵니다. 누르면 단계별 호출 내역이 열립니다.

Liner API가 주는 것은 검색 결과와 모델의 답입니다. 아래는 화이트체커가 직접 합니다.

- **출처 원문 수집**: 검색 결과의 요약은 근거로 쓰지 않습니다. 페이지를 직접 열어 본문에서 발췌를 잘라 냅니다. 보강 검색에서는 기관 사이트의 메뉴를 따라 안쪽 페이지도 엽니다([lib/gather](lib/gather), [lib/net](lib/net)).
- **출처 등급**: 공식 원문과 기관의 공식 안내는 1등급, 기관의 해설 글과 백과사전, 논문은 2등급, 보도와 블로그는 3등급입니다. 위키는 근거에서 뺍니다. 같은 자료를 옮겨 실은 출처는 하나로 묶습니다.
- **코드 규칙**: 모델의 판정을 규칙으로 다시 검사합니다. 모델이 낸 인용문이 발췌 안에 없거나, 유형에 필요한 등급의 출처가 없으면 판정을 낮춥니다([lib/judge/rules.ts](lib/judge/rules.ts)).
- **수정안 검사**: 모델은 어느 대목을 무엇으로 바꿀지만 내고, 문장은 코드가 그 대목만 바꿔 만듭니다. 원고에서 고칠 자리를 찾지 못했거나 추측을 나타내는 말이 사라지는 수정안은 보여 주지 않습니다([lib/merge/check.ts](lib/merge/check.ts)).
- **검증 기준**: 출처 등급, 유형마다 필요한 출처 수준, 판정 지침, 한정 표현 목록, 편집 우선순위는 코드와 떨어진 파일 하나에 둡니다([standards/culture-ko.json](standards/culture-ko.json)).

## 실행 방법

Node.js 24(이 버전에서 확인했습니다)와 Liner Platform의 API 키가 필요합니다.

```bash
git clone https://github.com/Jaden0104/whitechecker.git
cd whitechecker
npm ci
cp .env.example .env        # Windows에서는 copy .env.example .env
```

`.env`를 열어 `LINER_API_KEY`에 키를 넣습니다. `ACCESS_CODE`는 비워 둡니다.

```bash
npm run dev
```

1. 브라우저에서 <http://localhost:3000>을 엽니다.
2. 접속 코드 칸은 비워 둔 채 '가상 원고 불러오기'를 누르고 '검증 시작'을 누릅니다.
3. 1분쯤이면 검증이 끝납니다. 끝난 문장부터 판정표에 나타납니다. 가상 원고 한 편에 Liner 크레딧이 0.5달러쯤 듭니다.

빌드해서 실행하려면 `npm run build` 다음에 `npm start`를 씁니다.

## 확인용 도구와 측정

```bash
node tools/check_rules.mjs      # Liner를 부르지 않는 확인. tools/check_*.mjs 11개
node tools/measure.mjs http://localhost:3000 fixtures/small/manuscript.md fixtures/small/answers.json
```

`tools/measure.mjs`는 서버가 떠 있을 때 원고 한 편을 앱과 똑같이 돌리고, 정답지와 견줘 지표를 냅니다. Liner를 실제로 부릅니다.

시험 원고는 모두 직접 쓴 가상 원고이고, 틀린 곳을 일부러 심어 두었습니다.

- `fixtures/small`: 시연용 원고(정답 16개). 시작 화면의 '가상 원고 불러오기'로 열립니다.
- `fixtures/dev`: 개발용 원고(정답 51개). 프롬프트와 규칙을 고칠 때 이 원고로 쟀습니다.
- `fixtures/final`: 최종 확인용 원고. 프롬프트와 규칙을 고칠 때는 쓰지 않고, 마지막에 한 번만 쟀습니다.

| 지표 | 초기 목표 | 개발용 원고 | 최종 확인용 원고 |
| --- | --- | --- | --- |
| 명제 추출 누락률 | 10% 이하 | 0/51 | 0/49 |
| 잘못된 '일치' | 0건 | 0건 | 0건 |
| 잘못된 '불일치' | 0건 | 0건 | 1건. 미달 |
| 수정안의 새 오류 | 0건 | 수정안 10개에서 찾지 못함 | 수정안 7개 가운데 1건. 미달 |
| 경고 적중률 | 70% 이상 | 13/30(43%). 미달 | 13/33(39%). 미달 |
| 정상 문장의 추가 확인 부담 | 40% 이하 | 17/36(47%). 미달 | 19/33(58%). 미달 |
| 처리 시간 | 명제 100개에 5분 | 51개에 211초(100개로 치면 7분쯤). 미달 | 50개에 286초(100개로 치면 9분 30초쯤). 미달 |
| 비용 | 명제 100개에 3달러 | 51개에 2.32달러(100개로 치면 4.5달러쯤). 미달 | 50개에 2.44달러(100개로 치면 4.9달러쯤). 미달 |
| 편집자 작업 시간 | 한 번 재서 적음 | 재지 않음 | 30분 40초 |

- 개발용 원고의 값은 2026-11-22에 마지막으로 잰 한 번의 값입니다. 같은 원고도 돌릴 때마다 달라서, 추가 확인 부담은 36개 가운데 11~19건, 경고 적중률은 40~52%를 오갔습니다.
- 최종 확인용 원고의 값은 2026-11-24에 한 번 잰 값입니다. 잘못된 '불일치'와 수정안의 새 오류는 같은 문장에서 나왔습니다. 전시 안내와 보도자료가 건수를 다르게 적은 수치를, 앱이 보도자료를 따라 고치려 했습니다.
- 편집자 작업 시간은 작성자가 배포본에서 이 원고를 처음 보는 상태로, 검증이 끝난 뒤부터 내보낼 수 있게 될 때까지 잰 시간입니다. 도구 없이 검토한 시간과 비교하지 않았습니다.
- 목표는 재기 전에 정한 값 그대로 두었습니다. 미달인 항목도 그대로 적습니다.
- '0건'은 이 원고들에서 나온 결과이고, 오류가 없다는 뜻이 아닙니다.

## 한계

- 판정이 늘 맞는 것은 아닙니다. 맞는 문장에 '근거 부족'이나 '해석 주의', 드물게 '불일치'가 붙기도 하고, 실행할 때마다 결과가 조금씩 다릅니다.
- 열지 못하는 사이트가 있습니다. 접근을 거부하는 사이트는 다른 방법으로 다시 열지 않고 실패로 적습니다. 그 명제는 '근거 부족'으로 남습니다.
- 검증 기준은 한국어 문화·교양 분야 하나뿐입니다. 다른 분야에 쓰려면 기준 파일과 시험 원고를 새로 만들어 재야 합니다.
- 원고는 10,000자까지, 한 번에 명제 150개까지 처리합니다.
- 링크나 각주가 든 문장, 표와 캡션의 수정안은 원고에 자동으로 넣지 않고 '직접 반영할 항목'으로 알립니다.
- 편집 시간이 얼마나 줄어드는지는 아직 증명하지 못했습니다.
- 채택과 발송은 편집자가 정합니다. 문체 교정과 자동 발행은 하지 않습니다.

## 원고와 기록의 보관

- 서버는 원고와 판정을 저장하지 않습니다. 원고와 검토 기록은 그 브라우저에만 남고, 시작 화면의 '이 기기의 기록 삭제'로 지웁니다.
- 원고 내용은 Liner API로 전송됩니다. Liner Platform 약관상 API 입력은 모델 학습에 쓰이지 않으며, 보관과 삭제는 Liner의 정책을 따릅니다.
- 서버는 연 공개 웹 페이지의 본문을 메모리에 10분까지 두었다가 다시 씁니다. 원고와 명제, 판정은 두지 않습니다.
- 배포한 서버에서는 접속 코드가 맞아야 비용이 드는 경로가 동작합니다.

## 기존 결과물과 새로 만든 부분

- **기존(대회 전)**: 작성자가 뉴스레터 제작에서 써 온 검증 방법과 절차입니다. 팩트체크 기준 문서와 Claude Code 스킬(프롬프트)로 운용해 왔으며, 그 문서와 프롬프트는 이 저장소에 옮기지 않았습니다.
- **새로 만든 부분(2026-11-12~11-25)**: 이 저장소의 코드, 검증 기준(공개된 팩트체크 원칙과 작성자의 경험을 바탕으로 함), 프롬프트, 가상 원고와 정답지는 모두 대회 기간에 새로 썼습니다.
- **개발 도구**: 개발에는 AI 코딩 도구인 Claude Code를 썼습니다. 커밋 기록의 `Co-Authored-By` 표시가 그것입니다.

## 데이터와 라이선스

- `persona_validation/`은 기획 단계에서 가설을 점검하려고 한 합성 페르소나 조사입니다. 응답은 모두 모델이 만든 합성 응답이며 실제 사용자 조사가 아닙니다. 앱의 일부가 아니고, Liner API를 쓰지 않았습니다.
- 그 조사의 응답자 정보는 NVIDIA의 [Nemotron-Personas-Korea](https://huggingface.co/datasets/nvidia/Nemotron-Personas-Korea) 데이터셋(CC BY 4.0)에서 200명을 뽑고, 조사 조건을 덧붙인 것입니다.
- 시연과 측정에는 직접 쓴 가상 원고와 공개 웹 자료만 썼습니다. 회사 내부 자료와 개인정보는 들어 있지 않습니다.
- 화면 글꼴은 Pretendard(SIL Open Font License)입니다.
